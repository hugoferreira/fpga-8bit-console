# Boards

The console targets two FPGA boards from one set of RTL. This is what differs
between them, what each can and cannot do, and how to build for either.

Opened 2026-07-25, when the Tang Nano 20K target was added.

## Why there is a second board

`docs/memory-subsystem.md` states the blocker: the console's 64 KB main memory
is an on-chip array (`rtl/ram_async.sv`), 512 kbit against an iCE40 HX8K's
**128 kbit** of block RAM. yosys cannot map it, expands it into fabric as 1.7 M
AND gates, and place-and-route never finishes. `rtl/top.sv` therefore builds the
chip with `RAM_ADDR_BITS(13)` — an 8 KB memory — and says so in a comment that
begins "TEMPORARY, and it makes this bitstream non-functional": with 13 address
bits `$FFFC` and `$1FFC` are the same byte, so the reset vector aliases into the
program and no game can run.

That document proposes an external-memory abstraction as the fix, and it is
still the right fix for the BlackIce. But the same problem has a second answer
that costs no RTL at all: **a device with enough block RAM.** The Tang Nano 20K's
GW2AR-18C has 828 kbit in 46 blocks, and the 64 KB array maps to 32 of them.

So `rtl/top_tangnano20k.sv` passes `RAM_ADDR_BITS(16)` — the real machine, the
same value the simulator uses — and is the first bitstream in this project that
is a whole console rather than a measurement vehicle.

## The two boards

| | myStorm BlackIce MX | Sipeed Tang Nano 20K |
| --- | --- | --- |
| FPGA | Lattice iCE40 **HX8K** (tq144:4k) | Gowin **GW2AR-LV18QN88C8/I7** |
| Logic | 7,680 cells | 20,736 LUT4 |
| Flip-flops | 7,680 | 15,552 |
| Block RAM | 32 × 4 kbit = **128 kbit** | 46 × 18 kbit = **828 kbit** |
| Multipliers | none | 48 × 18×18 |
| Clock in | 25 MHz | 27 MHz |
| Main memory | **8 KB** — will not run a game | **64 KB** — the real machine |
| Audio out | 1-bit delta-sigma + external RC | onboard MAX98357A over I2S |
| Top | `rtl/top.sv` | `rtl/top_tangnano20k.sv` |
| PLL | `rtl/pll.v` (`SB_PLL40_CORE`, generated by `icepll`) | `rtl/pll_gowin.v` (`rPLL`, checked in) |
| Constraints | `rtl/top.pcf` | `rtl/tangnano20k.cst` |
| Toolchain | yosys + nextpnr-ice40 + icestorm | yosys + nextpnr-himbaechel + apicula |
| Build | `make all` | `make tangnano20k` |

Everything else — `chip.sv`, `clocks.sv`, `lcd.sv`, the CPU, the PPU, the PSG —
is shared verbatim. `make boards` prints a short form of this table.

## Building for the Tang Nano 20K

```
make tangnano20k                  # bin/toplevel.fs
make tangnano20k GAME=nemo        # GAME works here exactly as everywhere else
make tangnano20k-synth            # area report only, no place-and-route
make tangnano20k-prog             # load into SRAM (volatile)
make tangnano20k-flash            # write to the onboard 64 Mbit flash
```

### Toolchain

Four tools, none of them from the icestorm chain:

| Tool | Role |
| --- | --- |
| `yosys` | synthesis, `synth_gowin` — the same yosys as the iCE40 path |
| `nextpnr-himbaechel` | place and route, gowin uarch, `--device GW2AR-LV18QN88C8/I7 --vopt family=GW2A-18C` |
| `gowin_pack` | bitstream, from [Project Apicula](https://github.com/YosysHQ/apicula) (`pip install apycula`) |
| `openFPGALoader` | programming over the onboard BL616 debugger (`-b tangnano20k`) |

The least painful way to get a matched set on macOS or Linux is the
[YosysHQ oss-cad-suite](https://github.com/YosysHQ/oss-cad-suite-build) nightly
tarball, which ships all four already built against each other. A mix of
Homebrew formulae and a `pip` install works too, and drifts.

**It had drifted in this checkout, and the repair is worth writing down**
because the symptoms look nothing like "your toolchain is old":

| Symptom | Cause | Fix |
| --- | --- | --- |
| `nextpnr-himbaechel` aborts with `Library not loaded: …/libboost_system.dylib` | Boost 1.90 stopped shipping that library. It has been header-only since 1.69, so the binary references no symbols from it — only the load command remains | drop an empty stub dylib at `/opt/homebrew/opt/boost/lib/libboost_system.dylib` (`clang -dynamiclib -install_name <that path>`), or rebuild nextpnr |
| then `Library not loaded: …/python@3.13/…/Python` | Homebrew moved to 3.14 and removed 3.13 | `brew install python@3.13` |
| `gowin_pack: bad interpreter: …/python@3.11/bin/python3.11` | orphaned `pip` console scripts in `/opt/homebrew/bin` from a Python that no longer exists, shadowing anything newer on `PATH` | `pipx install apycula`, then move `/opt/homebrew/bin/gowin_{pack,pll,unpack}` out of the way — no formula owns them |

Neither of the first two is a Boost or Python problem in any real sense: they
are a binary compiled against a moving target and never relinked.

Note `GW2AR-18C` versus `GW2A-18C`. The `R` part is the same die with 64 Mbit of
SDRAM in the package, so nextpnr wants the full `GW2AR-LV18QN88C8/I7` part
string while both its chipdb (`--vopt family=`) and `gowin_pack -d` want the
plain `GW2A-18C`.

## Pin map

FPGA package pin numbers, which is how the board is labelled. Net names are the
board's, from the Tang Nano 20K datasheet v1.3 pinout. The authority is
`rtl/tangnano20k.cst`; this table is here to be read.

| Signal | Pin | Board net | Notes |
| --- | --- | --- | --- |
| `clk` | 4 | `SYS_CLK` | 27 MHz crystal |
| `key1` | 88 | `MODE0_KEY1` | S1 → button O (`$4007` bit 4) |
| `key2` | 87 | `MODE1_KEY2` | S2 → button X (`$4007` bit 5) |
| `led_reset` | 15 | `SYS_LED0` | active low; lit once reset is released |
| `led_lock` | 16 | `SYS_LED1` | active low; lit once the PLL locks |
| `scl` | 27 | `LCD_B7` | **wire to your panel** |
| `sda` | 28 | `LCD_B6` | **wire to your panel** |
| `cs` | 25 | `LCD_HS` | **wire to your panel** |
| `rs` | 26 | `LCD_VS` | **wire to your panel** |
| `lcd_rst` | 29 | `LCD_B5` | **wire to your panel** |
| `audio_pwm` | 30 | `LCD_B4` | 1-bit delta-sigma, needs an RC + amp |
| `i2s_bclk` | 56 | `I2S_BCLK` | onboard MAX98357A |
| `i2s_lrck` | 55 | `I2S_LRCK` | onboard MAX98357A |
| `i2s_din` | 54 | `I2S_DIN` | onboard MAX98357A |
| `pa_en` | 51 | `PA_EN` | MAX98357A `SD_MODE`, high = enabled |

The five LCD pins are the only thing an operator has to wire. They are five
consecutive positions on the left-hand 20-pin header, chosen because they are
adjacent on the connector and because their only other function is the RGB LCD
FPC — unused here, since this console drives a serial ST7789, not a parallel
panel. Move them freely; do **not** move them onto pins 80–85 (microSD) or 79
(the WS2812).

`nextpnr-himbaechel` requires every top-level port to be constrained — an
unassigned port is an error, not a warning — so the `.cst` and the port list of
`top_tangnano20k.sv` have to be kept in step.

## The clock

One rPLL, 27 MHz in, **112.5 MHz out, exactly**:

```
CLKOUT = CLKIN * (FBDIV_SEL + 1) / (IDIV_SEL + 1) = 27 * 25 / 6 = 112.5 MHz
VCO    = CLKOUT * ODIV_SEL                        = 112.5 * 8  = 900 MHz
PFD    = CLKIN / (IDIV_SEL + 1)                   = 4.5 MHz
```

VCO and PFD are both mid-window for a GW2A (400–1200 MHz and 3–400 MHz), so this
is not a marginal setting. Because 112.5 MHz is the *same* number `rtl/pll.v`
produces from the BlackIce's 25 MHz crystal, `rtl/clocks.sv` is unchanged and
so is everything derived from it: the chip at 112.5/32 = 3.515625 MHz, video at
60.155 Hz, the PSG's 22050 Hz virtual sample rate. 25/6 is the only small ratio
that lands on 112.5 from 27 MHz, and it lands on it with zero error.

The rPLL also provides the chip clock, on its second output:
`CLKOUTD = CLKOUT / 32 = 3.515625 MHz`. `rtl/clocks.sv` computes the same
division in a counter and the BlackIce build uses that, but a counter output is
not a clock network — see "the chip clock was not on a clock network" below for
the three hold violations that cost.

Use pin 4, the crystal — not the MS5351 generator on pins 10/11/13. Those are
programmed over I2C by the onboard BL616 and are reported not to bring an rPLL's
`LOCK` high when used as its reference.

## Audio

The board has a MAX98357A mono class-D amplifier wired to speaker pads, so
`rtl/i2s_out.sv` feeds it directly and the board makes sound with a speaker and
no other parts. Standard Philips I2S, 32-bit slots, BCLK = 112.5 MHz / 40 =
2.8125 MHz, LRCK = 43.945 kHz — inside the MAX98357A's 8–96 kHz window, and what
an integer division of the master clock gives. The same sample goes to both
slots because the amplifier's channel-select resistor is not broken out.

`rtl/dsigma.sv` is instantiated as well, on a header pin, so the BlackIce's
known-good output stage stays available if the I2S wiring is ever in doubt. It
needs an RC low-pass (~1k + ~10nF) and an amplifier off-board.

## Measured

`nextpnr-himbaechel`'s own device utilisation after place and route, which is
the authority (yosys's estimate via `make tangnano20k-synth` agrees on LUT4,
DFF and BSRAM exactly, and differs on ALU, which nextpnr pads to fill carry
chains):

```
    IOB           15/   384    3%
    LUT4        8493/ 20736   40%
    ALU         2218/ 15552   14%
    DFF         3231/ 15552   20%
    BSRAM         45/    46   97%      <- the tight one
    MULT18X18      1/    48    2%
    MULT9X9        3/    96    3%
    rPLL           1/     2   50%
```

`make tangnano20k-synth` adds the split that decides what the design can afford
next:

```
    block RAM by consumer:
      chip.ram.mem                       32 blocks
      chip.g_psg.psg0.aram                3 blocks
      chip.g_ppu.s0.display.ovl           2 blocks
      chip.g_ppu.s0.fetch.sheet           1 block
      chip.g_ppu.s0.lbuf.linebuf          1 block
      chip.g_ppu.s0.scan.list             1 block
      chip.g_ppu.s0.tmap.map_hi           1 block
      chip.g_ppu.s0.tmap.map_lo           1 block
      chip.g_psg.psg0.g_reverb.revbuf     1 block
      chip.g_psg.psg0.recip               1 block
      chip.g_psg.psg0.wrom                1 block
```

Three readings worth keeping:

- **Block RAM is the constraint, not logic.** 45 of 46, with the 64 KB main
  memory taking 32 of them. Logic sits at 40% of the device. The second overlay
  plane that `docs/hardware-gaps.md` gap 9 costs at "+5 blocks on the hx8k"
  has **one** block of headroom here, not five — the device is four times
  larger in logic and only six blocks larger than what this design already
  needs. Anything that wants more block RAM still has to earn it.
- **The multiply infers real DSP.** One `MULT18X18` and three `MULT9X9`, from
  the PSG's volume multiply, with no flags asked for. `docs/hardware-gaps.md`
  records under "Investigated and NOT recommended" that "the target device
  cannot help" because the hx8k has no `SB_MAC16` — true of that device, not of
  this one. A math coprocessor is a different conversation on a part with 48
  multipliers.
- **`ae37bbc` measured the whole design at 10,731 logic cells against the
  HX8K's 7,680 — 140%.** The same design is 40% of this device's LUT4s. The
  chip did not shrink; the device grew.

## Two timing results, one fixed and one not

The build runs nextpnr **without** a frequency target on purpose — `--freq`
applies one number to every unconstrained domain, and this design has three
that differ by 32x, so constraining `cpuclk` at the PSG's 112.5 MHz would report
a domain with 15x of margin as failing. `make tangnano20k` instead reads back
the per-domain Fmax nextpnr reports anyway and checks each against what
`rtl/clocks.sv` asks of it:

```
  timing, against what rtl/clocks.sv asks of each domain:
    pllclk       49.62 MHz achieved,   112.5000 needed   *** SHORT ***
    cpuclk       55.22 MHz achieved,     3.5156 needed   ok
    lcd0.cs     323.31 MHz achieved   (derived clock, no target)
```

### Fixed here: the chip clock was not on a clock network

The first routed build reported **three hold violations**, all in the PPU blit:

```
ERROR: Hold/min time violation for clock 'posedge cpuclk':
  clk-skew -2.04 -2.04 Net cpuclk (31,5) -> (1,13)
                       Sink chip.g_ppu.s0.blit.data64_q_DFFR_Q_10.CLK
```

`rtl/clocks.sv` makes the 3.515625 MHz chip clock by dividing the PLL output in
a counter, so the chip clock is a flip-flop output, and nextpnr routes that as
an ordinary signal: **2.04 ns of skew** corner to corner. Against a ~1.5 ns data
path that is a hold violation, which is a bitstream that does not work — not one
that is merely slow.

The fix is in `rtl/pll_gowin.v`: the rPLL divides internally and puts the result
on the clock network, where a clock belongs. `CLKOUTD = CLKOUT / 32` comes off
the same VCO as `CLKOUT`, so the 32:1 ratio and the phase lock `rtl/clocks.sv`
documents — a chip-clock signal stable for 32 PSG clocks, no synchroniser
anywhere — are exactly what they were. `clocks.sv` is still instantiated, for
its reset counter; its divider is left unconnected and yosys trims it.

Result: **0 hold violations**, and 294 fewer LUT4s.

**The BlackIce top has the same structure and has never been placed**, so nobody
has looked. `SB_PLL40_CORE` has no second divided output, so the fix there is a
global buffer (`SB_GB`) on the divided clock rather than a PLL setting.

### Not fixed here: the PSG's domain misses by 2.3x

**The PSG's clock domain closes at 49.62 MHz against 112.5 MHz.** This is the
same defect `refactor-build-targets` found on the hx8k, where the PSG alone
closes at **28.24 MHz** against the same clock. A device four times larger moves
a 4x miss to a 2.3x miss and no further, which settles the open question: *the
112.5 MHz PSG clock is not an hx8k problem, it is an RTL problem.* No board
fixes it.

The critical path is not the reciprocal path that was identified on the hx8k —
it runs from the reset counter through the arbiter's PSG select decode into the
PSG's per-channel reset logic, ~21 ns over ~31 levels with routing the majority
of it. So there is more than one path at this length, and pipelining only the
reciprocal may not be enough. Fixing it belongs to `refactor-psg-voice-pool`,
which owns the PSG datapath and has the golden-render gate to change it safely;
a board-support change is the wrong place.

`cpuclk` — the CPU, the PPU, the compositor, the video timing, everything at
112.5/32 = 3.515625 MHz — has **15.7x of margin**, so the console proper is
nowhere near the edge on this device.

## What is verified, and what is not

Verified in this checkout, on hardware-free tooling:

- **`make tangnano20k` completes**: `yosys -> nextpnr-himbaechel -> gowin_pack`
  produces a 7.3 MB `bin/toplevel.fs`, with **no timing errors and no hold
  violations**. Utilisation, timing and the critical path above are all read out
  of a real placed-and-routed netlist.
- **Block RAM initialisation survives to the routed netlist.** This was the
  open worry — every table in the design is `$readmemh`-loaded, and a bitstream
  that dropped those values would boot into nothing. Counted in
  `build/gowin/top_pnr.json`: 308 non-zero `INIT_RAM_*` words on
  `chip.ram.mem` (the program image), 48 on the PSG's wave ROM, 34 on the
  sprite sheet, 16 on the reciprocal table — and zero on `aram`, the tilemap,
  the line buffer, the overlay and the reverb buffer, which are working memory
  and correctly start empty.
- **`lcd.sv`'s `cs` routes.** The flip-flop output used as a clock is a real
  clock domain to nextpnr and closes at 323 MHz.
- The iCE40 path still synthesises (`synth_ice40` on `rtl/top.sv`, no errors).
- `make shot`, `make ppu-check` and `make test-65x02` all pass.

**Not verified: the board.** No `.fs` has been loaded onto hardware. Everything
below the bitstream is unproven — the pin choices for the SPI panel, the I2S
transmitter against a real MAX98357A, the key polarity, whether the ST7789 comes
up at all. Those need the board.

### One toolchain hazard you may hit

`nextpnr-himbaechel` (0.8-22-g226a2dfd) **segfaulted during routing** on two
placements of an earlier netlist, immediately after

```
Warning: Failed to route net 'chip.g_psg.psg0.sfx_id[3]_...' from X24Y42/LBO0
         to X25Y42/XD2 using dedicated routing.
```

— the fallback path it takes when a clock-enable net will not fit on the
dedicated resource. It is deterministic for a given placement and it is a tool
bug, not a design error: other seeds and other netlists route the same design
cleanly, and the netlist that ships does so at the default seed. If it happens
to you:

```
make tangnano20k GOWIN_SEED=2
```

Worth re-testing against a current nextpnr before spending any time on it.

## A naming constraint this target imposes

Gowin's cell library (`share/yosys/gowin/cells_sim.v`, read by `synth_gowin`)
occupies names an ordinary design might reach for, and yosys rejects the pair
outright rather than scoping around it. Two rules, both cheap to keep:

- **No module may be called `ALU`.** Gowin has a primitive of that name;
  a design module of the same name is `ERROR: Re-definition of module \ALU`.
  Same for `SP`, `DP`, `SDP`, `DQS`, `MUX2`, `LUT1`..`LUT4`, `DFF*`, `OSC`,
  `rPLL` — `grep -E '^\s*module\s+' share/yosys/gowin/cells_sim.v` is the list.
- **No `typedef enum` outside a module.** SystemVerilog puts it at
  compilation-unit (`$unit`) scope and takes its *items* with it, so a state
  enum written above a module makes `READ`, `WRITE`, `FETCH`… global names.
  Gowin's `DQS` primitive has a port called `READ`, and the pair is
  `ERROR: enum item \READ already exists`. Declaring the typedef inside the
  module removes the whole class of collision at once.

The Arlet core broke both, and this target originally carried the fixes:
`module ALU` → `module cpu6502_alu`, and its typedefs moved inside `module cpu`.
That core has since been retired (`3c0f2f8`, "the console runs on the new core,
and Arlet is gone") and `rtl/cpu6502_core.sv` breaks neither rule, so the fixes
went with the files. The rules are what is worth keeping: the iCE40 library has
no such names, so nothing on the BlackIce path will ever tell you when a new
module trips one.

Re-verified against the new core: `synth_gowin` on `rtl/top_tangnano20k.sv`
completes clean, and the area is within 1.5% of what the Arlet build measured.

## Not done

- **The 64 Mbit SDRAM in the GW2AR package is unused.** This target fits the
  console in block RAM instead, which is why it needs no memory controller. The
  abstraction in `docs/memory-subsystem.md` is still the right thing to build —
  it is what a *bigger* machine needs, and it is what the BlackIce needs to run
  anything at all — but it is no longer the only route to a working board.
- **No gamepad.** Two onboard keys read as O and X; the four directions read 0.
  The headers carry DS2 (PlayStation 2 controller) pins and the board is sold
  for retro gaming, so a DS2 reader is the obvious next thing.
- **HDMI is unused.** The console's video path is a serial ST7789; the board's
  TMDS output would want a different display path entirely.
- **No SDC.** `nextpnr-himbaechel` is run without timing constraints, so it
  reports estimated Fmax rather than checking a target.
