# Boards

The console targets three FPGA boards from one set of RTL. This is what differs
between them, what each can and cannot do, and how to build for any of them.

Opened 2026-07-25, when the Tang Nano 20K target was added. The Tang Primer 20K
was added 2026-08-06.

> **Status, 2026-08-06.** Both Gowin boards build, and **every timing domain
> passes on both**. Three separate defects were fixed to get here, and only the
> first two were blocking the build:
>
> 1. A **combinational loop** through the CPU core — `WE = we_c & RDY`, so a
>    stall predicate reading bus `rw` closed a cycle. Fixed at source in
>    `rtl/psg.sv`; see "The two defects that blocked both Gowin boards".
> 2. **52 block RAMs against the device's 46.** Every board top now builds with
>    `REVERB(0)`, which is a trade worth reading about before undoing.
> 3. **Both Gowin tops were clocking the PSG at 112.5 MHz instead of 18.75.**
>    They discarded `clocks.sv`'s divided `psgclk`. This invented the "PSG
>    misses its clock" story this document carried since July, *and* gave the
>    PSG 5102 clocks per sample instead of 850 — so these two bitstreams
>    rendered different audio from the BlackIce and the simulator. See
>    "Retracted: the PSG's domain misses by 2.3x".
>
> One loose end remains: `psgclk` does not land on a global clock network.
> It is harmless today (0 hold violations on both boards) but harmless by
> placement luck — details under the retraction.

## Why there is more than one board

`docs/memory-subsystem.md` states the blocker: the console's 64 KB main memory
is an on-chip array (`rtl/ram_async.sv`), 512 kbit against an iCE40 HX8K's
**128 kbit** of block RAM. yosys cannot map it, expands it into fabric as 1.7 M
AND gates, and place-and-route never finishes. `rtl/top.sv` therefore builds the
chip with `RAM_ADDR_BITS(13)` — an 8 KB memory — and says so in a comment that
begins "TEMPORARY, and it makes this bitstream non-functional": with 13 address
bits `$FFFC` and `$1FFC` are the same byte, so the reset vector aliases into the
program and no game can run.

That document proposes an external-memory abstraction as the fix, and it is
still the right fix for the BlackIce. But the same problem has a second answer
that costs no RTL at all: **a device with enough block RAM.** The Tang Nano 20K's
GW2AR-18C has 828 kbit in 46 blocks, and the 64 KB array maps to 32 of them.

So `rtl/top_tangnano20k.sv` passes `RAM_ADDR_BITS(16)` — the real machine, the
same value the simulator uses — and is the first bitstream in this project that
is a whole console rather than a measurement vehicle.

## The three boards

| | myStorm BlackIce MX | Sipeed Tang Nano 20K | Sipeed Tang Primer 20K + Dock |
| --- | --- | --- | --- |
| FPGA | Lattice iCE40 **HX8K** (tq144:4k) | Gowin **GW2AR-LV18QN88C8/I7** | Gowin **GW2A-LV18PG256C8/I7** |
| Package | TQFP144 | QFN88 | **PG256 BGA** — ball designators, not pin numbers |
| Logic | 7,680 cells | 20,736 LUT4 | 20,736 LUT4 |
| Flip-flops | 7,680 | 15,552 | 15,552 |
| Block RAM | 32 × 4 kbit = **128 kbit** | 46 × 18 kbit = **828 kbit** | 46 × 18 kbit = **828 kbit** |
| Multipliers | none | 48 × 18×18 | 48 × 18×18 |
| Clock in | 25 MHz | 27 MHz | 27 MHz |
| Main memory | **8 KB** — will not run a game | **64 KB** — the real machine | **64 KB** — the real machine |
| Audio out | 1-bit delta-sigma + external RC | onboard MAX98357A over I2S | Dock **PT8211 DAC** → 3.5mm jack |
| Top | `rtl/top.sv` | `rtl/top_tangnano20k.sv` | `rtl/top_tangprimer20k.sv` |
| PLL | `rtl/pll.v` (`SB_PLL40_CORE`, generated by `icepll`) | `rtl/pll_gowin.v` (`rPLL`, checked in) | `rtl/pll_gowin.v` — **the same file** |
| Constraints | `rtl/top.pcf` | `rtl/tangnano20k.cst` | `rtl/tangprimer20k.cst` |
| Toolchain | yosys + nextpnr-ice40 + icestorm | yosys + nextpnr-himbaechel + apicula | yosys + nextpnr-himbaechel + apicula |
| Build | `make all` | `make tangnano20k` | `make tangprimer20k` |

Everything else — `chip.sv`, `clocks.sv`, `lcd.sv`, the CPU, the PPU, the PSG —
is shared verbatim. `make boards` prints a short form of this table.

**The two Gowin boards are the same die.** The Tang Nano 20K's GW2AR-18C is the
Tang Primer 20K's GW2A-18C with 64 Mbit of SDRAM added inside the package: same
fabric, same 46 block RAMs, same 48 multipliers, and `apicula` and
`nextpnr-himbaechel` use the same `GW2A-18C` chipdb for both. Both boards also
run from a **27 MHz crystal**. That is why the third target cost so little —
`rtl/pll_gowin.v` is reused with no retune, every frequency `rtl/clocks.sv`
derives is identical, and the 64 KB main memory maps to 32 block RAMs the same
way. What actually differs is the package, the ext-board, and the audio DAC.

## Building for the Tang Nano 20K

```
make tangnano20k                  # bin/toplevel.fs
make tangnano20k GAME=nemo        # GAME works here exactly as everywhere else
make tangnano20k-synth            # area report only, no place-and-route
make tangnano20k-prog             # load into SRAM (volatile)
make tangnano20k-flash            # write to the onboard 64 Mbit flash
```

### Toolchain

Four tools, none of them from the icestorm chain:

| Tool | Role |
| --- | --- |
| `yosys` | synthesis, `synth_gowin` — the same yosys as the iCE40 path |
| `nextpnr-himbaechel` | place and route, gowin uarch, `--device GW2AR-LV18QN88C8/I7 --vopt family=GW2A-18C` |
| `gowin_pack` | bitstream, from [Project Apicula](https://github.com/YosysHQ/apicula) (`pip install apycula`) |
| `openFPGALoader` | programming over the onboard BL616 debugger (`-b tangnano20k`) |

The least painful way to get a matched set on macOS or Linux is the
[YosysHQ oss-cad-suite](https://github.com/YosysHQ/oss-cad-suite-build) nightly
tarball, which ships all four already built against each other. A mix of
Homebrew formulae and a `pip` install works too, and drifts.

**It had drifted in this checkout, and the repair is worth writing down**
because the symptoms look nothing like "your toolchain is old":

| Symptom | Cause | Fix |
| --- | --- | --- |
| `nextpnr-himbaechel` aborts with `Library not loaded: …/libboost_system.dylib` | Boost 1.90 stopped shipping that library. It has been header-only since 1.69, so the binary references no symbols from it — only the load command remains | drop an empty stub dylib at `/opt/homebrew/opt/boost/lib/libboost_system.dylib` (`clang -dynamiclib -install_name <that path>`), or rebuild nextpnr |
| then `Library not loaded: …/python@3.13/…/Python` | Homebrew moved to 3.14 and removed 3.13 | `brew install python@3.13` |
| `gowin_pack: bad interpreter: …/python@3.11/bin/python3.11` | orphaned `pip` console scripts in `/opt/homebrew/bin` from a Python that no longer exists, shadowing anything newer on `PATH` | `pipx install apycula`, then move `/opt/homebrew/bin/gowin_{pack,pll,unpack}` out of the way — no formula owns them |

Neither of the first two is a Boost or Python problem in any real sense: they
are a binary compiled against a moving target and never relinked.

Note `GW2AR-18C` versus `GW2A-18C`. The `R` part is the same die with 64 Mbit of
SDRAM in the package, so nextpnr wants the full `GW2AR-LV18QN88C8/I7` part
string while both its chipdb (`--vopt family=`) and `gowin_pack -d` want the
plain `GW2A-18C`.

The five LCD pins are the only thing an operator has to wire. They are five
consecutive positions on the left-hand 20-pin header, chosen because they are
adjacent on the connector and because their only other function is the RGB LCD
FPC — unused here, since this console drives a serial ST7789, not a parallel
panel. Move them freely; do **not** move them onto pins 80–85 (microSD) or 79
(the WS2812).

`nextpnr-himbaechel` requires every top-level port to be constrained — an
unassigned port is an error, not a warning — so the `.cst` and the port list of
`top_tangnano20k.sv` have to be kept in step.

## The clock

One rPLL, 27 MHz in, **112.5 MHz out, exactly**:

```
CLKOUT = CLKIN * (FBDIV_SEL + 1) / (IDIV_SEL + 1) = 27 * 25 / 6 = 112.5 MHz
VCO    = CLKOUT * ODIV_SEL                        = 112.5 * 8  = 900 MHz
PFD    = CLKIN / (IDIV_SEL + 1)                   = 4.5 MHz
```

VCO and PFD are both mid-window for a GW2A (400–1200 MHz and 3–400 MHz), so this
is not a marginal setting. Because 112.5 MHz is the *same* number `rtl/pll.v`
produces from the BlackIce's 25 MHz crystal, `rtl/clocks.sv` is unchanged and
so is everything derived from it: the chip at 112.5/32 = 3.515625 MHz, video at
60.155 Hz, the PSG's 22050 Hz virtual sample rate. 25/6 is the only small ratio
that lands on 112.5 from 27 MHz, and it lands on it with zero error.

The rPLL also provides the chip clock, on its second output:
`CLKOUTD = CLKOUT / 32 = 3.515625 MHz`. `rtl/clocks.sv` computes the same
division in a counter and the BlackIce build uses that, but a counter output is
not a clock network — see "the chip clock was not on a clock network" below for
the three hold violations that cost.

Use pin 4, the crystal — not the MS5351 generator on pins 10/11/13. Those are
programmed over I2C by the onboard BL616 and are reported not to bring an rPLL's
`LOCK` high when used as its reference.

## Audio

The board has a MAX98357A mono class-D amplifier wired to speaker pads, so
`rtl/i2s_out.sv` feeds it directly and the board makes sound with a speaker and
no other parts. Standard Philips I2S, 32-bit slots, BCLK = 112.5 MHz / 40 =
2.8125 MHz, LRCK = 43.945 kHz — inside the MAX98357A's 8–96 kHz window, and what
an integer division of the master clock gives. The same sample goes to both
slots because the amplifier's channel-select resistor is not broken out.

`rtl/dsigma.sv` is instantiated as well, on a header pin, so the BlackIce's
known-good output stage stays available if the I2S wiring is ever in doubt. It
needs an RC low-pass (~1k + ~10nF) and an amplifier off-board.

Three readings worth keeping:

- **Block RAM is the constraint, not logic.** 45 of 46, with the 64 KB main

  needs. Anything that wants more block RAM still has to earn it.

  multipliers.
- **`ae37bbc` measured the whole design at 10,731 logic cells against the
  HX8K's 7,680 — 140%.** The same design is 40% of this device's LUT4s. The
  chip did not shrink; the device grew.

## Two timing results, one fixed and one not

The build ran nextpnr **without** a frequency target, and reported:

```
  timing, against what rtl/clocks.sv asks of each domain:
    pllclk       49.62 MHz achieved,   112.5000 needed   *** SHORT ***
    cpuclk       55.22 MHz achieved,     3.5156 needed   ok
    lcd0.cs     323.31 MHz achieved   (derived clock, no target)
```

> **That table was not a timing result, and it is worth understanding why
> before trusting any Fmax number from this flow.** With no SDC, nextpnr places
> and routes against its **default 12 MHz target** — every one of those lines
> was printed as `(PASS at 12.00 MHz)` — hits it trivially, and then reports
> whatever critical path it happened to end up with. That is a lower bound taken
> under no timing pressure, not a measurement against 112.5 MHz. The giveaway
> arrived when the Tang Primer 20K target was added: the **same RTL on the same
> die** reported 43.05 MHz on one board and 55.31 MHz on the other. A 28% spread
> is placement noise being quoted as a design property.
>
> The reasoning for avoiding `--freq` was sound — it applies one number to every
> domain, and these differ by 32x, so `cpuclk` would be reported as failing with
> 20x of margin. The error was the conclusion: the fix for that is *per-clock*
> constraints, not an unconstrained estimate. Both boards now pass
> `--sdc rtl/gowin_boards.sdc`, so placement and routing are timing-driven at
> the real periods and `tools/gowin_timing.py` reports nextpnr's own PASS/FAIL
> instead of comparing against thresholds hand-copied into an awk script.
>
> **The PSG's miss survived the better method**, and there is a second finding
> underneath it. Re-measured on the Tang Primer 20K under a real 112.5 MHz
> constraint, the routed result is `pllclk` 43.05, `cpuclk` 70.48,
> `lcd0.cs` 294.55 MHz — **bit-identical to the unconstrained run, on all three
> clocks**. So the miss is real and this document's diagnosis stands.
>
> But identical-to-two-decimals is also evidence about the tool, and it admits
> two readings that have not been separated here: either the critical path is
> logic-depth-limited so no placement effort can help it, or
> `nextpnr-himbaechel`'s placer does not use the SDC target to drive
> optimisation and the constraint only changes the *report*. **Do not claim the
> first without testing it** — `--no-tmdriv` on the same netlist and seed is the
> experiment, and it has not been run.
>
> What the SDC definitely buys is the verdict: `FAIL at 112.50 MHz` instead of
> `PASS at 12.00 MHz`, against a target the design actually declares.

### Fixed here: the chip clock was not on a clock network

The first routed build reported **three hold violations**, all in the PPU blit:

```
ERROR: Hold/min time violation for clock 'posedge cpuclk':
  clk-skew -2.04 -2.04 Net cpuclk (31,5) -> (1,13)
                       Sink chip.g_ppu.s0.blit.data64_q_DFFR_Q_10.CLK
```

`rtl/clocks.sv` makes the 3.515625 MHz chip clock by dividing the PLL output in
a counter, so the chip clock is a flip-flop output, and nextpnr routes that as
an ordinary signal: **2.04 ns of skew** corner to corner. Against a ~1.5 ns data
path that is a hold violation, which is a bitstream that does not work — not one
that is merely slow.

The fix is in `rtl/pll_gowin.v`: the rPLL divides internally and puts the result
on the clock network, where a clock belongs. `CLKOUTD = CLKOUT / 32` comes off
the same VCO as `CLKOUT`, so the 32:1 ratio and the phase lock `rtl/clocks.sv`
documents — a chip-clock signal stable for 32 PSG clocks, no synchroniser
anywhere — are exactly what they were. `clocks.sv` is still instantiated, for
its reset counter; its divider is left unconnected and yosys trims it.

Result: **0 hold violations**, and 294 fewer LUT4s.

**The BlackIce top has the same structure and has never been placed**, so nobody
has looked. `SB_PLL40_CORE` has no second divided output, so the fix there is a
global buffer (`SB_GB`) on the divided clock rather than a PLL setting.

### Retracted: "the PSG's domain misses by 2.3x"

**This section used to assert that the PSG missed its clock by 2.3x on the Tang
Nano 20K and 4x on the hx8k, and that this was "not an hx8k problem, it is an
RTL problem. No board fixes it." That conclusion was wrong, and the error was
in this board port rather than in the PSG.**

The PSG was never asked to run at 112.5 MHz. `rtl/clocks.sv` divides the PLL by
`PSGDIV` for exactly this reason, in a comment that starts **"PSGDIV EXISTS
BECAUSE THE UNDIVIDED CLOCK DOES NOT CLOSE"**, and its default is 6 —
**18.75 MHz**. `rtl/top.sv` has always used it. Two more copies of the same
number sit in the tree: `rtl/target_psg.sdc` constrains `psgclk` to 53.333 ns,
and `clocks.sv` records `make synth-psg` measuring the PSG at Fmax 27.98 MHz.
Against 18.75 MHz, 27.98 is a **1.5x pass**, and the 28.24 MHz hx8k figure this
section quoted as a 4x failure is the same pass.

What actually happened is that both Gowin board tops threw the divided clock
away:

```
clocks clocks0(... .psgclk());     // divided psgclk discarded
assign psgclk = pllclk;            // the undivided 112.5 MHz
localparam PSG_CLK_HZ = 32'd112_500_000;
```

So the 112.5 MHz "requirement" was created by these two files, and every number
above was measured against it. Fixed 2026-08-06: both tops now take
`PSG_DIV = 6`, derive `PSG_CLK_HZ` from it so the divider and the sample rate
cannot drift apart, and connect `clocks.sv`'s `psgclk`.

**The second consequence was worse than the timing one and nothing would have
caught it.** `rtl/psg_timing.sv` derives the 22050 Hz sample tick from
`CLK_HZ`, so at 112.5 MHz the PSG had **5102 clocks per sample instead of 850**.
`docs/hardware-gaps.md` establishes that the sequencer gets whatever the walk
leaves over and that the number of phases in a visit is render-load-bearing —
so these two bitstreams were rendering **different audio** from the BlackIce and
from the simulator. No gate builds a board top, so no gate could see it.

Two things this does **not** retract:

- The critical path description below is still a real measurement of where the
  PSG's longest path runs. It is simply no longer a failing path.
- **`psgclk` does NOT get a global clock network, and this is the loose end.**
  It is a flip-flop output from `clocks.sv`'s modulo-6 divider, and
  `nextpnr-himbaechel` promotes `pllclk` ("global resources only") and `cpuclk`
  ("partially") but **not** `psgclk`. There is no lever to force it: `BUFG` does
  not exist in yosys's Gowin library, `synth_gowin` has no global-buffer
  insertion pass, and the gowin uarch exposes no `--vopt` for promotion.

  Measured `psgclk` skew, from the routed netlists:

  | Board | skew | hold violations |
  | --- | --- | --- |
  | Tang Nano 20K | 0.53 ns | 0 |
  | Tang Primer 20K | **1.06 ns** | 0 |

  Both build clean, so this is not a present fault. But it is clean *by
  placement luck* — the same design skews by 2x between two boards, and 2.04 ns
  is what produced three hold violations on `cpuclk`. Read a hold violation here
  as "the promotion did not happen", not as an RTL bug. **The robust fix is the
  second rPLL** (1 of 2 free): cascade it from 112.5 MHz at 1/6 — PFD 18.75 MHz,
  VCO 600 MHz at ODIV 32, both legal — making `psgclk` a real PLL clock. Its
  cost is that `PSGDIV` and the PLL settings become two places to keep in step,
  which is the drift `clocks.sv` warns detunes audio silently.

The critical path, as measured when the domain was over-constrained: it runs
from the reset counter through the arbiter's PSG select decode into the PSG's
per-channel reset logic, ~21 ns over ~31 levels with routing the majority of it
— so it is not the reciprocal path identified on the hx8k, and there is more
than one path at this length.

`cpuclk` — the CPU, the PPU, the compositor, the video timing, everything at
112.5/32 = 3.515625 MHz — has **15.7x of margin**, so the console proper is
nowhere near the edge on this device.

## What is verified, and what is not

Verified in this checkout, on hardware-free tooling:

- **`make tangnano20k GOWIN_SEED=2` completes**: `yosys ->
  nextpnr-himbaechel -> gowin_pack` produces a 7.3 MB `bin/toplevel.fs`, with
  **0 errors, 0 hold violations and 0 combinational loops**. Utilisation and
  timing above are read out of that placed-and-routed netlist.

  **The seed is not optional any more.** At the default seed 1 this board now
  hits the segfault described under "One toolchain hazard you may hit" below —
  which that section used to say the shipping netlist avoided. It no longer
  does, so on this board seed 2 is the working default until the tool is fixed.
  The Tang Primer 20K builds at seed 1; same design, different placement.
- **Block RAM initialisation survives to the routed netlist.** This was the
  open worry — every table in the design is `$readmemh`-loaded, and a bitstream
  that dropped those values would boot into nothing. Counted in
  `build/gowin/top_pnr.json`: 308 non-zero `INIT_RAM_*` words on
  `chip.ram.mem` (the program image), 48 on the PSG's wave ROM, 34 on the
  sprite sheet, 16 on the reciprocal table — and zero on `aram`, the tilemap,
  the line buffer, the overlay and the reverb buffer, which are working memory
  and correctly start empty.
- **`lcd.sv`'s `cs` routes.** The flip-flop output used as a clock is a real
  clock domain to nextpnr and closes at 323 MHz.
- The iCE40 path still synthesises (`synth_ice40` on `rtl/top.sv`, no errors).
- `make shot`, `make ppu-check` and `make test-65x02` all pass.

**Not verified: the board.** No `.fs` has been loaded onto hardware. Everything
below the bitstream is unproven — the pin choices for the SPI panel, the I2S
transmitter against a real MAX98357A, the key polarity, whether the ST7789 comes
up at all. Those need the board.

### One toolchain hazard you may hit

`nextpnr-himbaechel` (0.8-22-g226a2dfd) **segfaulted during routing** on two
placements of an earlier netlist, immediately after

```
Warning: Failed to route net 'chip.g_psg.psg0.sfx_id[3]_...' from X24Y42/LBO0
         to X25Y42/XD2 using dedicated routing.
```

— the fallback path it takes when a clock-enable net will not fit on the
dedicated resource. It is deterministic for a given placement and it is a tool
bug, not a design error: other seeds and other netlists route the same design
cleanly. **As of 2026-08-06 the Tang Nano 20K netlist no longer routes at the
default seed** — it segfaults with exactly this warning on `chip.mem_addr[2]`
and a PSG sequencer net, and needs `GOWIN_SEED=2`. The Tang Primer 20K, which
is the same design on the same die, routes fine at seed 1, so this tracks
placement luck rather than anything in the RTL. If it happens
to you:

```
make tangnano20k GOWIN_SEED=2
```

Worth re-testing against a current nextpnr before spending any time on it.

## Building for the Tang Primer 20K

```
make tangprimer20k                # bin/tangprimer20k.fs
make tangprimer20k GAME=nemo      # GAME works here exactly as everywhere else
make tangprimer20k-synth          # area report only, no place-and-route
make tangprimer20k-prog           # load into SRAM (volatile)
make tangprimer20k-flash          # write to the onboard flash
```

Same four tools as the Tang Nano path, same versions, same chipdb. Only three
things change: `--device GW2A-LV18PG256C8/I7` (the package differs, the die does
not), `rtl/tangprimer20k.cst`, and `rtl/top_tangprimer20k.sv`. `gowin_pack -d`
still wants the plain `GW2A-18C`, and `openFPGALoader -b tangprimer20k` is a
board this tool already knows.

### Before anything else: the DIP switch

**A Primer 20K on the Dock ext-board is dead out of the box until switch 1 of
the 5-position DIP switch is set to enable the core board.** Until then the
debugger cannot reach the FPGA's JTAG at all, so `openFPGALoader` finds nothing
and every symptom looks like a broken cable or a broken toolchain. Sipeed's own
wiki records it as the first thing to check. `openFPGALoader --detect` is the
one-line test — a working board answers:

```
idcode 0x81b
manufacturer Gowin
family GW2A
model  GW2A(R)-18(C)
irlength 8
```

Note the model string cannot tell a GW2A from a GW2AR: they share an IDCODE
because they are the same die.

### The core board is only the FPGA

The Primer 20K is a bare core board in a **DDR3 SODIMM outline**. It carries the
FPGA, its flash, the 27 MHz crystal and DDR3 — and no LED, no key, no connector
you can reach. Every peripheral belongs to whichever ext-board it is plugged
into, and there are two of them, the **Dock** and the **Lite**, with different
peripherals. `rtl/tangprimer20k.cst` targets the **Dock**.

This has a consequence worth stating plainly: **an FPGA ball designator tells
you nothing about where a wire physically goes.** The `.cst` therefore records
the ext-board's 204-position `CARD1` SODIMM position alongside each ball,
wherever that mapping is known.

### Pin map

Ball designators on the PG256, which is how the core board schematic is
labelled. `CARD1:n` is the position on the SODIMM edge connector; the net names
are the Dock's. The authority is `rtl/tangprimer20k.cst`; this table is here to
be read.

| Signal | Ball | CARD1 | Dock net | Notes |
| --- | --- | --- | --- | --- |
| `clk` | H11 | — | `sys_clk` | 27 MHz crystal, on the **core** board |
| `key1` | T10 | 15 | `btn_n0` | S → button O (`$4007` bit 4); the only 3.3 V key |
| `key2` | T3 | 165 | `btn_n1` | → button X (`$4007` bit 5); **1.5 V bank** |
| `led_reset` | L16 | 44 | `led0` | assumed active low; lit once reset is released |
| `led_lock` | L14 | 46 | `led1` | assumed active low; lit once the PLL locks |
| `scl` | F12 | ? | — | **wire to your panel** |
| `sda` | L15 | ? | — | **wire to your panel** |
| `cs` | C16 | ? | — | **wire to your panel** |
| `rs` | J13 | ? | — | **wire to your panel** |
| `lcd_rst` | G13 | ? | — | **wire to your panel** |
| `audio_pwm` | P12 | ? | — | 1-bit delta-sigma, needs an RC + amp |
| `hp_bck` | N15 | 36 | `HP_BCK` | PT8211 DAC |
| `hp_ws` | P16 | 34 | `HP_WS` | PT8211 DAC |
| `hp_din` | P15 | 30 | `HP_DIN` | PT8211 DAC |
| `pa_en` | R16 | 28 | `PA_EN` | LPA4809 enable, high = enabled |

Three of these deserve their reasoning rather than a table cell.

**`key2` is a 1.5 V input, and that is not a mistake.** The Dock has five user
keys and only `btn_n0` is in a 3.3 V bank; the other four sit in the bank the
Dock's DDR3 shares, so they must be declared `IO_TYPE=LVCMOS15` or the bank is
configured at the wrong voltage. Sipeed's own LiteX constraints declare them the
same way. This design instantiates no DDR3, but a bank's VCCIO is a board fact,
not a design choice. The other three keys are deliberately left alone: spending
balls on directions is a decision for whoever wires a real gamepad.

**The five LCD balls are reserved, not verified.** They are the balls Sipeed's
own `SPI_lcd` example uses to drive a serial panel — six signals, the shape of
one PMOD connector's eight — and not one of them collides with anything the Dock
assigns (HDMI, RGB FPC, Ethernet, microSD, LEDs, keys, headphone DAC), checked
against the full `CARD1` map. What is *not* established is which PMOD connector
they land on, because the `CARD1` positions of these six balls are absent from
every map available here; hence the `?` column. **Read them off the Dock
schematic before connecting a panel.**

**`audio_pwm` is on the example's backlight ball.** `rtl/lcd.sv` has no concept
of a backlight and never drives one, so that pin was free. If your panel needs a
switched backlight rather than a tie to 3V3, take P12 for it and move
`audio_pwm` to another free position on the same connector.

### Audio: a DAC, not an amplifier, and it is not I2S

The Tang Nano 20K carries a MAX98357A — a class-D amplifier with an I2S input —
so `rtl/i2s_out.sv` feeds it directly. The Dock instead carries a **PT8211**,
a 16-bit stereo DAC, into an **LPA4809** headphone amplifier and a 3.5mm jack.

**A PT8211 is not an I2S receiver, and the difference is not cosmetic.** Philips
I2S moves LRCK one BCK *before* the MSB of the slot it selects; a PT8211 moves
WS *coincident* with the MSB. With a 16-bit word in a 16-BCK half-frame there is
no padding to absorb that, so a Philips stream arrives across a slot boundary.
Measured, by driving `i2s_out.sv` into a PT8211 decoder in
`rtl/pt8211_out_tb.sv`: **`16'sh1234` comes out as `16'shdcbb`.** Not quiet, not
slightly wrong — noise.

So the Primer top instantiates `rtl/pt8211_out.sv`, the third output stage in
this design. The set now reads, by what the board carries:

| Board carries | Stage | Framing |
| --- | --- | --- |
| nothing | `rtl/dsigma.sv` | 1-bit density, RC + amp off-board |
| an I2S amplifier | `rtl/i2s_out.sv` | Philips, one-BCK delay |
| a PT8211 DAC | `rtl/pt8211_out.sv` | LSB-justified, no delay |

At `HALF = 40` on the 112.5 MHz `psgclk` this is BCK = 1.40625 MHz and a
43.945 kHz frame, next to the 1.536 MHz / 48 kHz Sipeed runs the same part at.
`rtl/dsigma.sv` is instantiated as well, on a header pin, so the BlackIce's
known-good output stage stays available — which matters more here than on the
Nano, because it is the only one of the three stages with a reference.

Its framing bench is not wired into a `make` target; run it directly:

```bash
iverilog -g2012 -s pt8211_out_tb -o build/pt8211_out_tb rtl/pt8211_out_tb.sv rtl/pt8211_out.sv && vvp build/pt8211_out_tb
```

The bench decodes exactly as the part does — sampling DIN on the **falling** edge
of BCK — and it discriminates: swap `i2s_out` in as the DUT and it fails.

### What is verified, and what is not

Verified in this checkout, on hardware-free tooling:

- **`synth_gowin` completes on `rtl/top_tangprimer20k.sv`**, and the area report
  matches the Tang Nano's to within the audio stage — same die, same design.
- **Every ball in `rtl/tangprimer20k.cst` is accepted by
  `nextpnr-himbaechel` for the PG256 part**, including the `LVCMOS15` key.
  This was checked rather than assumed: corrupting one ball to `Z99` gives
  `ERROR: Pin Z99 not found (pin# style)`, so the file is genuinely validated
  and not silently ignored.
- **`make tangprimer20k` completes.** yosys → `nextpnr-himbaechel` → `gowin_pack
  -d GW2A-18C` produces a 7.3 MB `bin/tangprimer20k.fs`, with **0 errors, 0 hold
  violations and 0 combinational loops**. This is the whole console — CPU, PPU,
  PSG, the full 64 KB main memory — not a reduced configuration.

  `nextpnr-himbaechel`'s own utilisation after place and route, which is the
  authority:

  ```
      IOB           15/   384    3%
      LUT4        8691/ 20736   41%
      ALU         2756/ 15552   17%
      DFF         2535/ 15552   16%
      BSRAM         46/    46  100%      <- no headroom at all
      rPLL           1/     2   50%
  ```

- **Timing — every domain passes**, against `rtl/gowin_boards.sdc`:

  ```
      cpuclk       54.57 MHz achieved,     3.52 needed   ok
      psgclk       44.59 MHz achieved,    18.75 needed   ok
      pllclk      245.40 MHz achieved,   112.50 needed   ok
      lcd0.cs     301.93 MHz achieved   (unconstrained, see the SDC)
  ```

  These are the numbers after the PSG clocking was fixed (see the retraction
  above). Before it, `pllclk` carried the whole PSG and was reported as
  43.05 MHz against a 112.5 MHz target this top had invented; now it carries
  only `clocks.sv`'s counters and closes at 245 MHz, while the PSG closes at
  44.59 against the 18.75 it actually needs — **2.4x of margin.**

- **Every ball in `rtl/tangprimer20k.cst` placed and routed** on the PG256, which
  is a stronger result than the packing-time acceptance noted above.

**Not verified: the board.** No `.fs` has been loaded onto this hardware.
Everything below the bitstream is unproven — and rather more of it than on the
Tang Nano, because more of it was inferred:

- **The LED polarity.** Assumed active low. Sipeed's board self-test drives
  these LEDs to all-ones at reset, which only makes sense if they are active
  low, and every other Tang board here is active low — but nobody has looked. If
  both LEDs stay dark on a board that is otherwise alive, drop the two
  inversions in `rtl/top_tangprimer20k.sv`; that is the whole fix.
- **The PT8211 framing against the real part.** It is right against Sipeed's own
  driver for this board and against a bench that models the datasheet's
  sampling edge. That is not the same as having heard it.
- **The five LCD balls**, as above.
- **That the Dock's headphone path is a PT8211 at all.** The evidence is
  Sipeed's `PT8211` example naming exactly these balls `HP_*`/`PA_EN`, plus the
  Dock's documented "3.5mm headphone jack, LPA4809MSF driver" — an *analog* amp,
  which implies a DAC in front of it. Consistent, but circumstantial.

## The two defects that blocked both Gowin boards

Both were in shared RTL, neither belonged to a board, and neither was new with
the Tang Primer 20K: they failed the Tang Nano 20K identically, from the same
tree, at the same point. Both are now fixed. They are written up because the
diagnosis is reusable and because one of the fixes constrains what you may do
next.

### 1. A combinational loop through the CPU core

`nextpnr-himbaechel` refused timing analysis outright:

```
Info: Found 1 combinational loops:
ERROR: Timing analysis failed due to combinational loops.
```

**This was never a Gowin problem.** `yosys -p "…synth_ice40…; check"` on
`rtl/top.sv` reported the same loop, in the same cells. yosys *warns* and
carries on, because it does no static timing analysis; nextpnr refuses. The
loop had been in the design the whole time on every board, and the only thing
that changed is that a Gowin board is the first target this project ever
actually placed. **Synthesising is not fitting**, and the iCE40 path
synthesising was never evidence that anything was sound.

The cycle, from yosys's own report:

```
psg.sv:180  assign rdy = !cpu_stall
  -> chip.sv  .rdy(cpu_rdy && psg_rdy)
  -> cpu6502_core.sv:768  assign WE = we_c & RDY
  -> memory_arbiter.sv  mem_write
  -> psg.sv:387  .rd_lvl(cs && !rw)
  -> psg_seq.sv:1481  cpu_sfx_rd_lvl
  -> psg_seq.sv:1506  cpu_stall
```

The comment immediately above `psg.sv:387` already described this hazard and
avoided it on the *write* side — "the 65C02 gates WE with RDY, so a stall
predicate that reads rw is a combinational loop through the CPU", which is why
`wr_pend` omits `rw`. The read side could not dodge it the same way, because
deciding "is this a read" is the whole point of `rd_lvl`, and it took the gated
`rw`.

**It was also a functional bug, not only a tool complaint.** Because `WE` is
`we_c & RDY`, a *write* that stalls drives `WE` low, so the bus reads as a read:
a stalled `$1x` write asserted the readback stall term and ran a spurious
state-memory readback.

The fix is to publish the write intent *before* the RDY gate and decide on that:

| File | Change |
| --- | --- |
| `rtl/cpu6502_core.sv` | new `WE_PEND` output = `we_c`, the ungated intent |
| `rtl/cpu6502_wrapper.sv` | passes it through as `write_pend` |
| `rtl/memory_arbiter.sv` | new `mem_write_pend`, muxed exactly like `mem_write` |
| `rtl/psg.sv` | new `rw_pend` input; `rd_lvl` is now `cs && !rw_pend` |

`we_c` is a function of registers that RDY holds frozen, so it is stable for the
whole stall and the cycle is cut at its only combinational link. **Only a slave
that produces RDY may use `mem_write_pend`** — a write enable driven from it
would commit repeatedly for the length of the stall. That is why it is a second
signal rather than a replacement.

`rtl/psg.sv`'s `aram_cpu_rd` still uses the gated `rw` and has the same blind
spot, deliberately: it is not in the loop, it only steers `dout`, and changing it
is an audio-path behaviour change that wants the golden gate.

### 2. Block RAM: 52 needed, 46 on the device

The Tang Nano target measured 45 of 46 when it was added; the design then grew
past the part, and placement died on the *PPU* — `ERROR: Unable to place cell
'chip.g_ppu.s0.tmap.map_hi.0.0', no BELs remaining to implement cell type 'DP'`
— because the PSG had taken the blocks first. The new consumer was the PSG
reverb history, `ringm` in `rtl/psg_walk.sv`: `PSG_NV` (8) slots x 732 samples x
16 bits, about 94 kbit, **exactly the 6 blocks that put it over**.

So every board top now builds with `REVERB(0)`, and that is the trade to
understand rather than a free win:

- **The console loses reverb on hardware.** The simulator does not — nothing
  overrides `REVERB` there, so `rtl/top_simulator.sv` still builds the default
  `REVERB(1)` and the audio gates continue to test the reverb path.
- **It buys headroom on the BlackIce too, and a lot of it**: `synth_ice40` on
  `rtl/top.sv` goes from **70 to 46** `SB_RAM40_4K`, and 10,056 to 9,869
  `SB_LUT4`. That board has 32 blocks and 7,680 cells, so it still does not fit
  — but reverb was most of what made it hopeless.
- **46 of 46 is zero headroom.** Anything that wants one more block has to find
  it first. The proportionate way back to reverb is a cheaper buffer — 16 bits
  per sample for a 33 ms delay line is generous — not a bigger device.

## A naming constraint the Gowin targets impose

Gowin's cell library (`share/yosys/gowin/cells_sim.v`, read by `synth_gowin`)
occupies names an ordinary design might reach for, and yosys rejects the pair
outright rather than scoping around it. Two rules, both cheap to keep:

- **No module may be called `ALU`.** Gowin has a primitive of that name;
  a design module of the same name is `ERROR: Re-definition of module \ALU`.
  Same for `SP`, `DP`, `SDP`, `DQS`, `MUX2`, `LUT1`..`LUT4`, `DFF*`, `OSC`,
  `rPLL` — `grep -E '^\s*module\s+' share/yosys/gowin/cells_sim.v` is the list.
- **No `typedef enum` outside a module.** SystemVerilog puts it at
  compilation-unit (`$unit`) scope and takes its *items* with it, so a state
  enum written above a module makes `READ`, `WRITE`, `FETCH`… global names.
  Gowin's `DQS` primitive has a port called `READ`, and the pair is
  `ERROR: enum item \READ already exists`. Declaring the typedef inside the
  module removes the whole class of collision at once.

The Arlet core broke both, and this target originally carried the fixes:
`module ALU` → `module cpu6502_alu`, and its typedefs moved inside `module cpu`.
That core has since been retired (`3c0f2f8`, "the console runs on the new core,
and Arlet is gone") and `rtl/cpu6502_core.sv` breaks neither rule, so the fixes
went with the files. The rules are what is worth keeping: the iCE40 library has
no such names, so nothing on the BlackIce path will ever tell you when a new
module trips one.

Re-verified against the new core: `synth_gowin` on `rtl/top_tangnano20k.sv`
completes clean, and the area is within 1.5% of what the Arlet build measured.

## Not done

- **The 64 Mbit SDRAM in the GW2AR package is unused.** This target fits the
  console in block RAM instead, which is why it needs no memory controller. The
  abstraction in `docs/memory-subsystem.md` is still the right thing to build —
  it is what a *bigger* machine needs, and it is what the BlackIce needs to run
  anything at all — but it is no longer the only route to a working board.
- **The Tang Primer 20K's Lite ext-board is not supported.** `rtl/tangprimer20k.cst`
  targets the Dock. The Lite has 2 keys rather than 5, no HDMI, no Ethernet and
  **no headphone jack** — so a Lite port needs its own constraints and would
  fall back to `rtl/dsigma.sv` for audio. The core board, the crystal, the PLL
  and the top are all reusable; only the `.cst` and the audio instantiation are
  not.
- **The Primer 20K's DDR3 is unused**, as is the Nano's SiP SDRAM, for the same
  reason: this design fits in block RAM and needs no memory controller.
- **No gamepad.** Two onboard keys read as O and X; the four directions read 0.
  The headers carry DS2 (PlayStation 2 controller) pins and the board is sold
  for retro gaming, so a DS2 reader is the obvious next thing.
- **HDMI is unused.** The console's video path is a serial ST7789; the board's
  TMDS output would want a different display path entirely.
- **No generated clocks in the SDC.** `rtl/gowin_boards.sdc` now constrains
  `pllclk` and `cpuclk`, but `nextpnr-himbaechel` rejects
  `create_generated_clock` outright, so two clocks that are phase-locked by
  construction (`cpuclk` is `pllclk`/32 off the same VCO) have to be declared as
  unrelated primaries. Every cross-domain path nextpnr reports between them is
  therefore analysing a crossing that cannot happen, and `lcd0.cs` — a
  flip-flop output used as a clock — stays unconstrained for the same reason.
  The two same-domain verdicts are the ones that mean something.
