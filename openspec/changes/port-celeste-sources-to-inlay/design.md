## Context

The compatibility implementation checked in an Inlay layout wrapper, a copied
main body, and four migrated modules, but left the direct customasm corpus in
the production directory. Unchanged handwritten modules and generated data
were still consumed with raw `#include` paths into that legacy tree. The result
assembled correctly but did not satisfy “the full Celeste game written in
Inlay.”

Inlay intentionally accepts architecture-specific target instructions. A file
does not need to replace every 6502 mnemonic with a semantic operation to be
Inlay source; it needs to participate in the Inlay module graph and use Inlay
declarations where the language provides them.

## Goals / Non-Goals

**Goals:**

- Make `src/celeste/` contain one obvious production representation.
- Give every Celeste source/data module the `.inlay.asm` suffix.
- Use Inlay `include` for every handwritten instruction module.
- Preserve the typed object layout, 66 typed accesses and structured `obj_ptr`.
- Keep the legacy direct assembler input outside production source solely for
  live equivalence testing.
- Preserve the complete 64 KiB image and functional behavior.

**Non-Goals:**

- Add a native Inlay instruction encoder.
- Replace target-specific 6502 instruction bodies with portable operations.
- Translate generated byte tables into a different data-description language.
- Change game behavior, data, addresses, or instruction selection.

## Decisions

### Use a flat production module graph

The production directory contains:

```text
src/celeste/
  main.inlay.asm
  layout.inlay.asm
  memmap.inlay.asm
  math.inlay.asm
  obj.inlay.asm
  collide.inlay.asm
  player.inlay.asm
  room.inlay.asm
  draw.inlay.asm
  fx.inlay.asm
  sound.inlay.asm
  gfx.inlay.asm
  rooms.inlay.asm
  audio.inlay.asm
```

`main.inlay.asm` is the only game entry. It includes the layout and every
handwritten instruction module with Inlay `include`. A flat tree avoids the
misleading distinction between “real” legacy modules and a partial `inlay/`
overlay.

### Treat generated data as Inlay modules

Graphics, room, and audio files contain target data directives rather than
layout-aware operations, but they are still part of the source graph. Their
generators emit `.inlay.asm` so that the production tree has one convention.
Inlay passes their target directives through without changing bytes.

The portable frontend intentionally represents expanded source positions with
16-bit slices, so the complete 116 KiB corpus cannot be expanded into one
semantic source buffer. `memmap`, `gfx`, `rooms` and `audio` are therefore the
exact allowlist of opaque target includes. They contain declarations and data,
not Inlay semantic operations. All four remain production `.inlay.asm` files;
only their contents bypass semantic parsing. The parsed layout and handwritten
instruction graph remains below the portable limit.

### Relocate, do not retain, the legacy production corpus

The former `.asm` tree moves to
`tests/inlay/reference/celeste-customasm/`. Its main file adjusts only the
relative ISA include paths needed by the new location. It is never used by
`make GAME=celeste hex`; conformance alone assembles it.

Keeping the oracle provides a live first-byte diagnostic. Keeping it under
`src/celeste/` would preserve the ambiguity this change exists to remove.

### Enforce source-boundary invariants in conformance

Before assembly, conformance checks that:

- every regular file in `src/celeste/` ends in `.inlay.asm`;
- every local dependency names a checked-in `.inlay.asm` module;
- only `memmap`, `gfx`, `rooms` and `audio` use opaque target includes;
- production sources never reference the test oracle or a legacy Celeste
  `.asm` path;
- the expected production module set is exact.

It then checks construct counts, direct-reference byte equality, the 65,536
byte size, and the golden digest.

### Preserve external target definitions and opaque data

The layout module may retain raw `#include` directives for the console ISA
files under `src/isa/`. Those are backend definitions outside the Celeste
corpus and are not legacy game-source dependencies. The main module may use
raw target includes only for the four allowlisted declaration/data modules
described above.

## Risks / Trade-offs

- [The test oracle duplicates the old game] → Keep it clearly test-only and
  immutable except when an intentional byte change updates both paths.
- [Generated tools or documentation may keep old filenames] → Search the
  repository for every former Celeste `.asm` path and update production-facing
  references.
- [Metrics could accidentally measure the oracle] → Point the Celeste corpus
  registry explicitly at the production `.inlay.asm` modules.
- [A local raw include could reintroduce a hybrid port] → Enforce an exact
  four-file opaque include allowlist in conformance.

## Migration Plan

1. Snapshot the current direct customasm corpus into the test reference tree
   and verify its original digest from the new location.
2. Flatten the maintained wrapper/body/modules into the final production
   `.inlay.asm` module graph.
3. Convert unchanged handwritten and generated modules without changing their
   target text.
4. Update asset generators, build dependencies, metrics, tests and docs.
5. Add source-boundary assertions and retain comparative plus golden gates.
6. Run strict OpenSpec validation, Inlay tests, Celeste functional tests,
   forced production build, and repository searches for stale production
   paths.

Rollback restores the mixed tree and prior build selection; the reference
snapshot preserves the original source throughout migration.
